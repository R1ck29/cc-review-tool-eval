# 本評価の限界

結論を社内展開する前に、この評価が**測っていないこと**を明示しておく。

## 0. 初回の盲検レビューは無効だった（ベンチマーク側の欠陥）

最初にベンチマークを作った際、各欠陥に `# [D08] column is discount_percent, not discount_pct`
のような**答えを書いたコメントを埋めていた**。読みやすさのつもりだったが、
これはレビュアーに答案用紙を渡すのと同じ。

盲検レビューを1件流した時点で発覚した。レビュアーの出力に明示されている：

```
"the in-file annotation says it's named `discount_percent` in `schema.sql`"
"The docstring contains leftover defect annotations ([D04], [D08])"
```

diff-only（`schema.sql` が文脈に無い戦略）でも D08 を「検出」してしまい、
文脈再現率の予測と矛盾した。これで気づいた。

**対処**: 全アノテーションを除去（`bench/repo_annotated_backup/` に旧版を保存）、
欠陥が発火することを再確認、グラフを再構築、文脈再現率が不変であることを確認したうえで
盲検レビューを再実行した。

**教訓**: 自社リポジトリで同種のベンチマークを作る場合、
欠陥の説明はコード内ではなくマニフェスト側（`bench/defects.json` に相当）に置くこと。
コメントに書いた瞬間、そのベンチマークは検出率を測れなくなる。

## 1. 測ったのは「文脈再現率」であって「検出率」ではない

`harness/run_bench.py` が判定するのは
**欠陥を見るのに必要なファイルが文脈に入ったか**であり、
LLM が実際にその欠陥を指摘したかではない。

- 文脈に入らなければ検出は不可能 → **品質の上限**として厳密
- 文脈に入っても LLM が見落とす → 実際の検出率は必ずこの値**以下**

つまり表の数字は楽観側の上限。`graph` の 67% は「67% 検出できる」ではなく
「**どんなに良いモデルでも 67% までしか届かない**」を意味する。

利点は決定論的であること（実行ごとの分散ゼロ）。
社内 A/B が有意差を出せない原因である LLM の実行間分散を、この指標は完全に回避する。

**上限としても楽観側に寄っている**：`harness/quality_report.py` の測定で
blast radius の precision は平均 13%（返すファイルの 87% は無関係）。
ノイズが多い文脈ほど LLM の検出率は落ちるので、実検出率は再現率よりさらに下がる。

**実検出率は未測定**。測るには12個の欠陥を知らない盲検レビュアーが必要で、
本評価では API 認証情報がなく実行できていない。手順は下記「実検出率の測り方」を参照。

## 2. ベンチマークが小さい

15ファイル・12欠陥・Python のみ。実リポジトリは桁が違う。

影響の方向:
- **トークン削減率**は実リポジトリでもっと大きくなる（全読みの分母が増えるため）。
  実測 2.3x は小規模リポでの値で、大規模では改善する。
  ただし `diff-only` との比較（グラフの方が高い）は規模によらず成立する。
- **`impact` のバグ**はリポジトリ規模と無関係。import の書き方だけで決まるので、
  実リポジトリでも同じ割合で発生する。むしろ大規模ほど `from pkg import module` が増える。
- **欠陥クラスの構成比**は自社リポジトリで測り直すべき。
  L/X/H の比率がここでの 4:3:5 と違えば、総合再現率も変わる。

**推奨**: `bench/defects.json` の形式で自社の実 PR から
過去に見逃した指摘を 30〜50 件書き起こし、同じハーネスを回す。

## 3. トークン数は推定値

`est_tokens()` は 4文字=1トークンの近似。実トークナイザではない。
戦略間の**比**を見る用途では問題ないが、絶対値を課金予測に使わないこと。

## 4. Ix は機能検証のみ、実運用検証はしていない

Ix はバックエンドを起動して `map` / `impact` / `search` を実行し、
下表の範囲で挙動を確認した。ただし失格判断は技術評価ではなく
**バックエンドが監査不能である**という一点による。
性能・安定性・大規模リポでの挙動は評価していない。

## 5. Serena / semgrep は実測していない

README で推奨した Serena（LSP経由）と semgrep は、
アーキテクチャ上の推論であって本評価では実行していない。
Serena が `from pkg import module` を正しく解決するという主張は
「LSP は意味解決を行う」という性質からの推論であり、未検証。
採用前に同じハーネスで実測すること。

## Ix の実測結果（参考）

失格判断とは別に、技術的には以下が確認できた。**公平を期して記載する。**

| ケース | code-review-graph | Ix |
|---|---|---|
| D05 `compute_total` の呼び出し元特定 | ❌ `impact` が取りこぼす | ✅ `Callers: create_order` を正答 |
| D07 クラス変更の依存先 | ✅ | ✅ `importers=2 dependents=2` |
| D11 `getattr` 動的ディスパッチ | ✅（偶発的な import エッジ経由） | ❌ `callers=0` |
| D09 トピック文字列の不一致 | ❌ | ❌（`search` は名前類似で拾うが impact ではない） |

**シンボル単位の影響解析は Ix の方が正確。**
code-review-graph の `impact` バグはここで明確に不利。

ただし H クラス（文字列結合）は **両者とも取りこぼす**。
静的コードグラフである以上、実装によらない原理的限界であることが
2つの独立実装で確認できた。
→ 文字列契約チェックは、どちらを選んでも別途必要。

## 実検出率の測り方（未実行・要 API 認証情報）

文脈再現率は上限でしかない。実際の検出率を測るには、**欠陥を知らないレビュアー**が要る。
評価者本人（欠陥を仕込んだ側）はレビュアーになれない。

手順:

1. 各戦略（diff-only / graph / graph+callers / +文字列プリパス / full-repo）について、
   `results/crg_depth2.json` の `graph_files` が示すファイル群だけを文脈として組む
2. 欠陥マニフェストを**渡さずに**「このPRをレビューして問題を列挙せよ」と指示する
3. 返ってきた指摘を `bench/defects.json` の12件に突き合わせて採点する
4. 各戦略 × 各欠陥で n=5 程度反復し、実行間分散を出す

注意点:
- **同一モデル・同一 effort で揃える**。effort を変えると検出率が動く
- 採点は指摘テキストと欠陥の対応付けが必要で、ここに主観が入る。
  採点者を分けるか、採点基準を先に文書化すること
- 誤検知（false positive）も数える。再現率だけ上げても
  ノイズだらけのレビューは実務で使われなくなる

本評価では `ANTHROPIC_API_KEY` も `ant` CLI も利用できなかったため未実施。
社内で回す場合は自社リポジトリの実欠陥に置き換えたほうが、
このベンチマークより直接的な結論が出る。
