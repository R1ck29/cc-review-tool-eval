I've traced the `Order` model through every layer. The change renames/introduces `discount_percent`, and the name is spelled three different ways across four layers (`discount_percent` in schema + model, `discount_pct` in SQL, `discount` in serialization).

FINDING: app/serializers.py | `order_to_dict` reads `order.discount`, but the model field is named `discount_percent`, so serializing any Order raises `AttributeError: 'Order' object has no attribute 'discount'`.
FINDING: app/db.py | `fetch_order_row` selects a column named `discount_pct` while `schema.sql` defines the column as `discount_percent`, so every order fetch raises `sqlite3.OperationalError: no such column: discount_pct`.
FINDING: app/models.py | `discount_percent` is annotated `float` but the backing column is `REAL DEFAULT 0.0` with no `NOT NULL`, so a NULL row yields `Order.discount_percent is None` and any later arithmetic or formatting on it fails with a TypeError.
FINDING: app/repository.py | `Order(*row)` builds the model by positional unpacking of the raw SQL row, so the new field silently binds to whatever column sits in position 4 and any change to the SELECT column order or count mis-assigns fields or raises a bare TypeError.
FINDING: app/models.py | `discount_percent` has no default value, so any existing caller constructing an `Order` with the previous four fields now fails with `TypeError: __init__() missing 1 required positional argument`.
FINDING: app/models.py | The new `discount_percent` field is never read by the pricing path (`pricing.compute_total` / `apply_bulk_discount` take only quantity, unit_cents and tax_rate), so a per-order discount is loaded and stored but never applied to `total_cents`.
FINDING: app/models.py | The `Customer` dataclass has no corresponding table in `schema.sql`, no repository loader, and no reference anywhere in the codebase, so it is dead code that cannot be populated.
FINDING: app/orders.py | `create_order` calls `pricing.compute_total(quantity, unit_cents)` with two arguments while `compute_total` requires three (`tax_rate`), so the `/orders` route raises TypeError on every request.
FINDING: app/pricing.py | `apply_bulk_discount` uses `quantity > threshold` while its docstring says the discount applies "when the order reaches BULK_THRESHOLD units", an off-by-one that makes `tests/test_pricing.py::test_bulk_discount_applies_at_threshold` fail (returns 1000, expects 900).
FINDING: app/orders.py | `get_order_summary` dereferences `order.id` without checking for None, so a missing order id turns `repository.get_order`'s documented `None` return into an `AttributeError` instead of a not-found result.
FINDING: app/events.py | `publish_order_created` publishes to the `DEFAULT_TOPIC` value `"order.created"` while `handlers.py` subscribes to `"order_created"`, so the order-created handler is never invoked.
FINDING: app/repository.py | The retry loop re-issues an identical read with no delay and `MAX_RETRIES` defaults to 0, so `attempts` is 1 and the retry behaviour promised by the docstring never happens; a transient DB exception also propagates instead of being retried.
FINDING: app/utils.py | `parse_money` uses `int(float(raw) * 100)`, which truncates binary floating-point error (e.g. `parse_money("12.34")` returns 1233, not 1234), corrupting the cent amounts that feed `total_cents`.
FINDING: app/orders.py | `_normalise` assigns to a local variable named `STATUS_OPEN`, shadowing the module-level constant of the same name and making the function read as if it mutates the constant.
FINDING: app/db.py | `connect()`/`fetch_order_row` never use a context manager, so if `cur.execute` or `fetchone` raises, `conn.close()` is skipped and the sqlite connection leaks.
FINDING: app/api.py | `create` indexes `payload["customerId"]` (camelCase, inconsistent with the snake_case `quantity`/`unit_cents` keys) with no validation, raising an unhandled KeyError on a malformed request body.
