Reviewed `app/events.py` (18 lines: `subscribe`, `publish`, new `publish_order_created` + new `from app.config import get`), plus its blast radius from the graph — `app/handlers.py` (only `subscribe` caller), `app/config.py`, and the `tests/` tree. Note: the graph is stale (built 2026-08-11 at SHA `fa2f35c`), so I verified every graph claim against the files on disk.

The central problem is a topic-string mismatch between the new publisher and the only existing subscriber.

FINDING: app/events.py | `publish_order_created` publishes to `get("DEFAULT_TOPIC")` which resolves to `"order.created"` (dot), but the only subscriber in `app/handlers.py:9` registers `on_order_created` under `"order_created"` (underscore), so the handler is never invoked and every order-created event is silently dropped.
FINDING: app/handlers.py | The subscription topic literal `"order_created"` at line 9 was not updated to match the new config-driven `DEFAULT_TOPIC` value `"order.created"`, leaving the publish/subscribe wiring permanently disconnected.
FINDING: app/events.py | `publish` uses `_SUBSCRIBERS.get(topic, [])` and returns nothing, so publishing to a topic with zero subscribers is a silent no-op with no error, log, or return value — which is exactly what hides the topic mismatch above at runtime instead of failing loudly.
FINDING: app/events.py | `get("DEFAULT_TOPIC")` relies on `app/config.py:get`'s `default=None`, so if `DEFAULT_TOPIC` is ever removed or misspelled in `SETTINGS`, `publish_order_created` calls `publish(None, payload)` and silently drops the event rather than raising a `KeyError`.
FINDING: app/events.py | `publish_order_created` has zero callers anywhere in the repo (confirmed via `callers_of` and a repo-wide grep) — `app/orders.py:create_order` never publishes — so the new function is dead code and the order-created event is never emitted even if the topic were correct.
FINDING: app/events.py | Naming a *specific* event's topic `DEFAULT_TOPIC` couples `publish_order_created` to a generic fallback setting; any future change to `DEFAULT_TOPIC` for an unrelated purpose will silently redirect order-created events to the wrong topic.
FINDING: app/events.py | `publish` invokes subscribers with no exception isolation, so a single raising subscriber aborts delivery to all later subscribers for that topic and propagates the error into `publish_order_created`'s caller.
FINDING: app/events.py | `publish` iterates the live list returned by `_SUBSCRIBERS.get(topic)` rather than a copy, so a subscriber that calls `subscribe()` for the same topic during dispatch mutates the list mid-iteration and can be re-entrantly invoked or loop unboundedly.
FINDING: app/events.py | `_SUBSCRIBERS` is mutated by `subscribe` and read by `publish` with no locking, so concurrent use in a threaded service can raise `RuntimeError: dictionary changed size during iteration` or lose registrations.
FINDING: app/events.py | `subscribe` appends unconditionally with no dedupe and there is no `unsubscribe`, so a module imported/reloaded twice registers the same callback twice and delivers duplicate events, with no way to ever remove a handler.
FINDING: app/handlers.py | The subscription is a module-level import side effect, so `publish_order_created` invoked before anything imports `app.handlers` finds an empty subscriber list and drops the event — an import-ordering hazard the new publisher makes reachable.
FINDING: tests/test_pricing.py | The test suite contains only `test_bulk_discount_applies_at_threshold`; there is no test covering `publish`, `subscribe`, or the new `publish_order_created`, which is why the topic mismatch ships undetected.
FINDING: app/events.py | New module-level dependency `from app.config import get` makes the event bus depend on global config state at call time, so `publish_order_created` is untestable without monkeypatching `app.config.SETTINGS` and cannot target a topic explicitly.
