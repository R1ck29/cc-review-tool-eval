Reviewed `app/utils.py` against the surrounding call graph. Findings below (target file first, then context files):

FINDING: app/utils.py | `parse_money` multiplies a binary float by 100 and truncates with `int()`, so common money strings lose a cent — `parse_money("0.29")` returns 28 and `parse_money("1.15")` returns 114; it should use `Decimal` or `round()`.
FINDING: app/utils.py | `int()` truncates toward zero rather than rounding, so any input with sub-cent precision is silently floored (`parse_money("12.999")` → 1299) with no error or warning about the discarded fraction.
FINDING: app/utils.py | Truncation toward zero makes rounding direction asymmetric across sign — `parse_money("12.345")` → 1234 but `parse_money("-12.345")` → -1234, so a debit and its matching credit do not net to zero.
FINDING: app/utils.py | `parse_money` has no input validation or error handling: `None` raises `TypeError`, `"$12.34"` or `""` raises `ValueError`, and neither is caught or converted to a domain error, so a bad payload field surfaces as a 500.
FINDING: app/utils.py | `parse_money` accepts non-decimal float literals that a money parser should reject — `"1e3"` silently becomes 100000 cents, `"inf"` raises `OverflowError`, and `"nan"` raises `ValueError`.
FINDING: app/utils.py | `parse_money` has no docstring contract or guard for values already in cents, so calling it on an integer cents value (e.g. the raw `unit_cents` from the API payload) silently inflates the amount by 100x.
FINDING: app/utils.py | `clamp` silently returns `low` when callers pass an inverted range (`low > high`) instead of raising `ValueError`, hiding argument-order mistakes such as `clamp(x, 100, 0)`.
FINDING: app/utils.py | `clamp` is unsafe for `NaN`: `clamp(float("nan"), 0, 1)` returns `0` (and `clamp(0.5, float("nan"), 1)` returns `nan`) because `min`/`max` comparisons with `NaN` are order-dependent rather than propagating.
FINDING: app/utils.py | Neither helper is imported anywhere in the service — `app/api.py` passes `payload["unit_cents"]` straight through without `parse_money`, and `discount_percent` is never bounded with `clamp` — so this module is dead code and the parsing/bounding it was written for still does not happen.
FINDING: tests/test_pricing.py | There is no test file covering `app/utils.py` at all, so the rounding, sign, and error-path behavior of `parse_money`/`clamp` is entirely unverified.
FINDING: app/pricing.py | `compute_total` requires three positional arguments but `app/orders.py:create_order` calls it as `pricing.compute_total(quantity, unit_cents)`, so every `POST /orders` request raises `TypeError: compute_total() missing 1 required positional argument: 'tax_rate'`.
FINDING: app/pricing.py | `apply_bulk_discount` uses `quantity > threshold` while its docstring says the discount applies when the order "reaches" the threshold, an off-by-one that makes the existing test `apply_bulk_discount(10, 100) == 900` fail (it returns 1000).
FINDING: app/db.py | The `SELECT` reads a column named `discount_pct`, but `schema.sql` defines the column as `discount_percent`, so `fetch_order_row` raises `sqlite3.OperationalError: no such column: discount_pct` on every call.
FINDING: app/db.py | `conn.close()` is not in a `try/finally` or `with` block, so any exception from `cur.execute`/`fetchone` (including the bad-column error above) leaks the SQLite connection.
FINDING: app/serializers.py | `order_to_dict` reads `order.discount`, but the `Order` dataclass field is `discount_percent`, so serializing any order raises `AttributeError`.
FINDING: app/handlers.py | The handler subscribes to the topic `"order_created"` while `events.publish_order_created` publishes to `DEFAULT_TOPIC` = `"order.created"`, so the handler is never invoked and the event is silently dropped.
FINDING: app/repository.py | With `MAX_RETRIES` set to `0` the loop runs exactly once, so the documented retry behavior is inert; the loop also retries a deterministic query with no backoff, meaning retries could never help even if configured.
FINDING: app/repository.py | `get("MAX_RETRIES") + 1` raises `TypeError` if the key is ever absent from `SETTINGS`, because `config.get` returns `None` by default instead of a numeric fallback.
FINDING: app/orders.py | `get_order_summary` dereferences `order.id` without checking for `None`, so a missing order id turns `repository.get_order`'s `None` return into an `AttributeError` instead of a not-found result.
FINDING: app/orders.py | `_normalise` assigns to a local named `STATUS_OPEN`, shadowing the module constant of the same name — misleading code that reads as if it mutates the constant while actually doing nothing of the sort.
FINDING: app/orders.py | `create_order` never persists the order and returns a dict with no `id`, so the created order can never be fetched back by `repository.get_order` and `serializers.order_to_dict` cannot serialize it.
FINDING: app/api.py | `create` indexes `payload["customerId"]`, `payload["quantity"]`, and `payload["unit_cents"]` with no validation, so a missing or non-numeric field raises an uncaught `KeyError`/`TypeError`; note also the inconsistent camelCase vs snake_case key naming.
FINDING: app/tasks.py | `run_task` builds an attribute name from caller-controlled input and `getattr`s it off the `handlers` module without checking that the result is callable or an allow-listed handler, so a name like `"order_created.__class__"`-style probing or a non-function module attribute leads to an unexpected object being called.
FINDING: app/events.py | `publish` iterates subscribers with no exception isolation, so one failing subscriber prevents all later subscribers from receiving the event; it also iterates the live list, so a subscriber that calls `subscribe` mutates the list during iteration.
FINDING: app/config.py | `SETTINGS` is a mutable module-level dict exposed via a plain `get`, giving any importer the ability to mutate global configuration at runtime with no validation or immutability guarantee.
