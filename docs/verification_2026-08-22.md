## 2. 結論を変える穴（新規発見）

### A. コスト計算から `impact` の出力そのものが抜けている ★最重要

`run_bench.py` は blast radius が**選んだファイル**のトークンだけを数え、
**ツールが返す JSON 本体**を数えていない。これは会話に入る tool result なので、
実際には課金対象の文脈である。`cost_model.py` の `GRAPH_PAYLOAD = 680` も
実測値ではなく、ファイル側のトークン数（681）が誤って入っていた。

実測（`harness/payload_cost.py` を追加）:

| リポジトリ | depth | 選択ファイル | ファイル | **payload** | 合計 | 全読み比 |
|---|---|---|---|---|---|---|
| bench/repo (15f) | 2 | 42% | 482 | **3,198** | 3,680 | **0.3x（全読みより3倍高い）** |
| 実リポ 192f/975k | 1 | 3% | 45,077 | **84,174** | 129,251 | 7.5x |
| 実リポ 192f/975k | 2 | 29% | 383,577 | **278,349** | 661,926 | **1.5x** |

- **ベンチマーク上では、payload を数えた瞬間に「2.3倍安い」が「3.3倍高い」に反転する。**
- 実リポの depth 2（本評価が全編で使った設定）は**単一呼び出しで233,604トークン**を返す
  （`max_results` 既定500ノード・`truncated: true`）。Opus の窓に入らない。
- depth 1 なら 7.5倍削減で実用範囲。**社内導入するなら depth 1 が既定であるべき。**

さらに: **MCP ツール `get_impact_radius_tool` は `max_results` を公開していない**
（`main.py:220`、CLI の `--max-results` のみ）。既定500固定なので、
MCP 経由では payload を絞れない。**CLI+skill 運用が必須**（ツール定義税7,615トークンとは別の理由）。
`detail_level="minimal"` は209トークンまで落ちるが `impacted_files` を返さないので、
文脈組み立てには使えない。

参考実測（実リポ・depth 2）: `max_results` 500→233,604 / 100→55,215 / 50→30,742 / 20→17,025 トークン。
20 まで絞っても、9ファイルを名指しするのに 17k トークン払う。

### B. ベンチマークの import 偏りを補正したら、推奨構成が変わる（前回「未測定」の項目）

前回 README は「ベンチは B形式 43.8%（実コードの10倍）なので graph に不利。
ただし**どれだけ改善するかは未測定**」で止まっていた。測った。

`harness/make_style_a.py` で B を 43.8% → 6.2% に補正した等価コピーを生成
（欠陥は `verify_defects.py` で FIRES 9 / LATENT 2 / STATIC 1 と一致することを確認済み）:

| 実害9件 | graph（元/補正後） | graph+callers（元/補正後） |
|---|---|---|
| X クラス | 67% → **100%** | 100% → 100% |
| H クラス | 0% → 33% | 33% → 33% |
| **合計** | **56% → 78%** | **78% → 78%** |

**`callers_of` 併用の上乗せがゼロになる。** 実コードの import 分布では
`impact` 単体で graph+callers と同じ検出率に届く。
README の推奨（「`callers_of` 併用を CLAUDE.md に明記」）は、
自社リポの B 率が高い場合にのみ意味がある — まず `import_style.py` で測ること。

副産物: D11 が graph で HIT→**MISS** に転じた。元の HIT は
「`from app import X` が `app/__init__.py` を指す」というバグ由来の
**過剰包含による偶然の当たり**だった。バグは recall を下げるだけでなく、
一部の HIT を水増ししてもいた。

### C. `string_contracts.py` は実リポジトリで機能しない

「今日すぐ試せる・0円・0トークン」と推奨していたが、**実リポで動かした形跡がなかった**。

実行した結果:
- 3リポ中2リポで **IndexError クラッシュ**（空の SELECT 断片）
- `.venv` を除外しないため 13ファイルのプロジェクトで 8,069ファイルを走査し、
  2分でも終わらない（キー突合が O(n²)）

両方修正した（`SKIP` 追加＋正規化インデックス化、bench の結果3件は不変、実リポ1〜2秒）。
修正後の実測が本題:

| リポジトリ | 指摘 | 内訳 |
|---|---|---|
| 実リポ 192f | **14件（真陽性 0）** | 9件: DDL が `.sql` でなく Python 文字列内にあるため実在カラムを未定義と誤判定 / 5件: `Content-Type` vs `Content-type`、`mcpServers` vs `mcp_servers` など意図的な差異 |
| Megatron-LM-ABEJA | 0件 | — |
| agent_eval | 0件 | — |

**`cost_rework.py` の「＋文字列プリパス = 検出率100%・指摘件数は増えない（15.7件）」は
社内リポでは支持できない。** 15ファイルのベンチでは DDL が `schema.sql` にあり、
命名衝突も仕込んだものだけだったから3件全部が真陽性になっただけ。
月$15,318 の節約はこの行に依存している。

### D. 「文脈再現率が実検出率を完全予測」は一部が定義上の同義

盲検の採点基準は「**相手側のファイル/シンボルを名指ししたか**」。
相手側が文脈になければ原理的に満たせないので、
文脈再現率と検出率が一致するのは部分的に**構成上の必然**であって、経験的発見ではない。
加えて n=9・1反復（LLM側の分散は未測定）、L クラス3件は全戦略100%で情報量ゼロ。
実質の情報は X/H の数セルしかない。

「決定論的指標で A/B は不要」は強すぎる。
**言えるのは「文脈にないものは検出できない（上限として使える）」まで。**

### E. `import_style.py` はパースできないファイルを黙って捨てる

Python 3.8 で実行すると 7ファイルが SyntaxError で無言スキップされ、
B 件数が 59→52 に減る（156ファイル中149しか見ない）。
**社内リポで古い Python から回すと過小評価する。** 実行前に `python -V` を確認すること。

### F. README のトークン表が別リポの数字

README「コスト実測」表（full-repo 1,556 / graph 681 / graph+callers 769 / diff-only 132）は、
引用元の `results/crg_depth2.json` の値（1,100 / 489 / 551 / 93.5）と一致しない。
1,556 は**注釈付きの旧ベンチ `bench/repo_annotated_backup`**（答えをコメントに書いていて破棄したもの）の
トークン数。比率（2.3x / 11.8x）は保たれているので結論は変わらないが、絶対値は差し替えが必要。

### G. star数に裏付けデータがない

README の候補表の star 数（code-review-graph 29.8k、serena 27.8k、repomix 27.8k …）は
`results/` に根拠がなく、オフラインでは検証できない。
serena と repomix が同値なのも不自然。**社内提出前に再取得すること。**

## 4. 推奨の修正

1. **`impact` は depth 1・`--max-results` 小さめ・CLI 経由**。depth 2 既定のままだと
   単一呼び出しで20万トークン超を返す。MCP 経由では絞れない。
2. **`callers_of` 併用は自社リポの B 率を測ってから**。0〜3.7% なら上乗せ効果はほぼない。
3. **文字列プリパスを「検出率100%・追加コスト0」として計上しない**。
   現状の実装は実リポで偽陽性のみ。semgrep 等の実績あるルールベースに置き換えて再測定すること。
4. **金額（月$15,318）は撤回して損益分岐だけ残す**。3 が崩れると総額が変わる。
5. 変わらないもの: **Ix 不採用**（監査不能なバイナリ）、**code-review-graph の外部通信要件適合**、
   **`impact` の import 解決バグの存在と機序**、**H クラス（文字列結合）はグラフでは原理的に取れない**。
