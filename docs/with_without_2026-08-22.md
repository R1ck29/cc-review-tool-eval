# code-review-graph あり / なし — どちらが良いか

2026-08-22。前回までの評価は「文脈の作り方」を比較していた（`impact` が組んだファイル集合 vs 差分だけ）。
**それは「なし」の定義が間違っている。** 素の Claude Code は差分を眺めるだけではなく、grep と読み込みで
呼び出し元を探す。ここでは**同じエージェント・同じリポジトリ・同じプロンプトで、
MCP を繋ぐか繋がないかだけを変えて**測り直した。

観点は6つ: ①検出品質 ②コスト ③スケール ④運用の失敗モード ⑤機密性 ⑥導入負荷。

---

## 観点3: スケール — ここが決定的（決定論的実測）

15ファイルのベンチマークでは、どちらの側の性質も出ない。
同じ12欠陥を **316ファイル**（60個の合成サービスパッケージで包んだもの、`harness/make_scaled_repo.py`）
に埋め直して測った。欠陥は同一（`verify_defects.py` で FIRES 9 / LATENT 2 / STATIC 1 一致）。

### 3-1. blast radius が壊れる

| リポジトリ | blast radius 平均 | precision | 明らかに無関係なファイル |
|---|---|---|---|
| 15ファイル | 6.0 ファイル | 13.2% | 0 |
| **316ファイル** | **36.0 ファイル** | **11.9%** | **30.0（`services/*`）** |

`services/*` の60パッケージは **app を一切 import していない**（生成器の仕様）。
にもかかわらず blast radius に入るのは、名前が衝突しているから。極端な例:

```
impact --files app/events.py --depth 2
  → 185 ファイル（services/* が 180、app/ が 5）
  → 本当に必要な app/handlers.py は入っていない
```

**無関係な180ファイルを返し、唯一必要な1ファイルを落とす。**

### 3-2. 推奨していた回避策（`callers_of`）がスケールで壊れる

前回の推奨は「`impact` のバグは `query callers_of` の併用で埋まる」だった。
名前で引く仕組みなので、**名前が衝突した瞬間に使えなくなる**:

```
15ファイル:  callers_of compute_total → status=ok,        results=1  (app/orders.py::create_order)
316ファイル: callers_of compute_total → status=ambiguous, results=0, candidates=20（全部“定義”）
```

決定論的な文脈再現率（実害9件）:

| | 15ファイル | 316ファイル |
|---|---|---|
| graph | 56% | 56% |
| **graph + callers** | **78%** | **56%** |

**スケールすると `callers_of` の上乗せがゼロになる。**
（前回の再検証で「import 形式を実コード分布に直すと上乗せが消える」ことも判明済み。
上乗せが残るのは「小さくて、かつ B形式 import が多い」リポだけ。）

### 3-3. コストも逆転する

`impact` が返す JSON 自体を数えると（`harness/payload_cost.py`）:

| リポジトリ | 選択ファイル | payload | 合計 | 全読み比 |
|---|---|---|---|---|
| 15ファイル | 482 | 3,198 | 3,680 | **0.3x（全読みより高い）** |
| 316ファイル | 19,105 | 51,122 | 70,227 | **0.6x（全読みより高い）** |
| 実リポ 192f/975k depth1 | 45,077 | 84,174 | 129,251 | 7.5x |
| 実リポ 192f/975k depth2 | 383,577 | 278,349 | 661,926 | 1.5x |

同じ探索を grep でやった場合のコスト（316ファイル）:

```
grep compute_total  → 362 hits / 22,509 トークン   ← 一番ノイズの多いケース
grep get_order      → 183 hits / 10,505 トークン
grep customerId     →   1 hit  /     56 トークン   ← H クラス（文字列結合）は grep が最強
```

**グラフに映らない H クラスは、grep なら1発で当たる。**
`impact` が同じ質問に51,122トークン払っているのに対し、56トークン。

## 観点4: 運用の失敗モード（実測）

### 4-1. グラフは黙って古くなる

```
app/invoices.py を新規作成（app.pricing.compute_total を呼ぶ）→ 再ビルドしない
  query callers_of compute_total → ['orders.py::create_order']   ← 新しい呼び出し元が見えない
  impact --files app/pricing.py  → invoices.py なし、警告フィールドもなし
```

`impact` の応答に stale を示すフィールドは無い（`status: ok` のまま）。
**古い答えを、古いと分からない形で返す。** grep には起こらない失敗。

### 4-2. `update` は git 依存で、未 add のファイルを拾わない

```
git 管理外のディレクトリ: WARNING: git diff failed → 0 files updated（終了コードは正常）
git 管理下・未 add     : 0 files updated           ← 新規ファイルは見えないまま
git add 後            : 1 files updated            ← ここで初めて反映
```

作業ツリーをレビューする使い方（Claude Code の標準的な使い方）では、
**新規ファイルが graph に存在しない状態でレビューが走る。**

### 4-3. レビュー専用の入口も同じバグを踏む

本ツールが `CLAUDE.md` で推奨している `get_review_context_tool` を
`app/pricing.py` に当てると、返るのは
`config.py, db.py, events.py, repository.py, test_pricing.py, utils.py`（4,809トークン）。
**唯一の呼び出し元 `app/orders.py` は入らない。** `impact` と同じ import 解決バグ。

### 4-4. 保存領域

| リポジトリ | ソース | graph.db |
|---|---|---|
| 実リポ 192ファイル | 11 MB | **123 MB** |
| 316ファイル（合成） | 1 MB | 11 MB |

エッジ表とその索引5本で104MB（42,869エッジ = 1エッジ約2.5KB）。
ID に絶対パス付き完全修飾名を使っているため。社内の大規模リポでは GB 級を見込むこと。

## 観点1: 検出品質 — エージェント実測（Claude CLI・18ラン・$8.67）

`harness/agent_review.py`。両アームとも **同じリポジトリの使い捨てコピーで動く実際の Claude Code**。
違いは MCP を繋ぐか否かだけ。

- なし（`agent`）: `Read` `Grep` `Glob` のみ。`.code-review-graph/` はコピーから除外
- あり（`agent+graph`）: 上記 ＋ MCP 4ツール。プロンプトで `get_impact_radius_tool` と
  `query_graph_tool(callers_of)` を先に使うよう指示

トランスクリプトで実使用を確認済み（あり側は全ラン `get_impact_radius_tool` 1回＋`query_graph_tool` 2〜3回）。

| クラス | n | なし | あり |
|---|---|---|---|
| L 単一ファイル | 3 | 100% | 100% |
| X ファイル跨ぎ・静的エッジ | 3 | **100%** | 100% |
| H 文字列/動的結合 | 3 | 67% | 67% |
| **合計** | 9 | **89%** | **89%** |

**9欠陥すべてで判定が一致した。** 唯一の見逃し（D10 `customerId`/`customer_id`）も両方。

前回報告の「なし 33% vs あり 78%」は、**「なし」側の手を縛った結果**だった
（`blind_review.py` は全アームで Read/Grep を禁止していた）。
素の Claude Code は grep で呼び出し元を辿る。X クラス3件は、なし側が全部自力で当てている。

### コストは「あり」が5割高い

| | $/レビュー | ターン | 指摘/件（中央値） | 実時間 |
|---|---|---|---|---|
| なし | **$0.386** | 15.1 | 14 | 64秒 |
| あり | **$0.577 (+49%)** | 18.3 | 12 | 65秒 |

トランスクリプトから、**グラフはファイル読み込みを減らしていない**:

| | ファイル系ツール呼び出し | MCP 応答トークン | ファイル応答トークン |
|---|---|---|---|
| なし | 10.3回 | 0 | 889 |
| あり | 11.2回 | **5,126** | 1,000 |

**「グラフを見たので読まずに済む」は起きない。** グラフの応答が丸ごと上乗せされる。

### 手戻り込みの総費用（`harness/decide.py`・実測値のみを入力）

| | 検出率 | トークン | トリアージ | 手戻り | 合計/PR | 合計/月 |
|---|---|---|---|---|---|---|
| なし | 89% | 0.39 | 14.00 | 13.33 | 27.72 | 5,544 |
| あり | 89% | 0.58 | 12.00 | 13.33 | 25.91 | 5,182 |

差は月 $362 で「あり」が安いが、**これは検出率ではなく指摘件数14 vs 12の差**（n=9・1反復）で、
ほぼ確実にノイズ。**検出率が同じである以上、金額差に意味のある符号はない。**

## 結論 — まず「この実験では差を測れていない」

**検出率 89% vs 89% は「差がない証拠」ではない。この設計には差を検出する力が最初から無い。**
`harness/compare_arms.py`:

```
対応ペア n=9 : どちらか一方だけが当てたペア = 0
McNemar 正確検定 p = 1.000
```

不一致ペアがゼロなので、検定は何も判定していない。設計の検出力:

| 真の差 | この設計 (n=9) の検出力 | 80%検出に必要なペア数 |
|---|---|---|
| 5pt | **0%** | 157 |
| 10pt | **0%** | 78 |
| 20pt | **0%** | 39 |
| 30pt | 3% | 25 |
| 50pt | 25% | — |

（「なし側だけが当てる」ケースを0と仮定した、**ツールに最も有利な**計算）

**つまり「あり」が10pt良かったとしても、この実験は 0% の確率でしか気づけない。**
前回の `power.py` が「n<200 の『有意差なし』は無情報」と言っていたのと同じ罠に、
今回は自分で嵌まっていた。

### 差が出ないように設計されてしまっていた点（ツールに不利な方向）

1. **天井効果**: 9件中8件を両アームが当てた。差がつく余地がほぼない
2. **弁別できるのは実質3件だけ**: L クラス3件は単一ファイル（道具不要）、
   H クラス3件はグラフに原理的に映らない（＝ツールが負けると分かっている種類）。
   実際に差がつきうるのは X クラス3件のみ
3. **15ファイルのリポ**: grep が一発で終わる規模。ツールの主張は規模で効く
4. **単一ファイル変更のみ**: 実PRは複数ファイルで、blast radius の価値が出やすい
5. **反復1回**: 二次指標では run 内変動（-6 〜 +8）がアーム間差（+2）より大きい。
   1回のドローで 89% vs 89% になっただけで、78% vs 100% だった可能性も同じくらいある
6. **採点は仕込んだ12件限定**: グラフ側が拾った「仕込み以外の本物の問題」は加点されない

二次指標（1レビューが報告した仕込み欠陥の総数、12件中）でも
合計 なし33 / あり35（符号検定 p=1.000）で、やはり分離しない。

### 現時点で言えること / 言えないこと

| | |
|---|---|
| **言える** | 15ファイル・単一ファイル変更では、素の Claude Code が grep で X クラスを全部当てた。前回報告の「なし 33%」は baseline を縛った測り方の産物 |
| **言える** | レビュー1回あたりの費用は「あり」が +49%（$0.386 → $0.577）。グラフはファイル読み込みを減らさず、MCP 応答 5,126トークンが純増 |
| **言える** | 316ファイルでは blast radius の 83% が偽陽性、`callers_of` は ambiguous で機能停止（決定論的実測・分散なし） |
| **言えない** | **品質が同じかどうか。** 「あり」がやや良い可能性は、このデータでは否定できていない |
| **言えない** | 大規模リポ・複数ファイル変更での優劣 |

**前節までの「入れる理由がない」は言い過ぎ。正しくは「入れる理由も入れない理由も、
この実験では出ていない。ただしコストの +49% と運用の失敗モードだけは実測で出ている」。**

### 差を実際に測るための設計（次にやること）

1. **弁別できる欠陥だけを増やす**: X クラス（ファイル跨ぎ・静的エッジあり）を30〜40件。
   L と H を混ぜると天井と床で薄まる。必要ペア数は 20pt差なら39、10pt差なら78
2. **規模を上げる**: `harness/make_scaled_repo.py`（316ファイル）か社内リポ。
   grep が数百ヒットを返す状況で初めてツール側の主張が試される
3. **複数ファイル変更のPRにする**
4. **反復3回以上**: 上の run 内変動を見るかぎり1回では読めない
5. **決定論的指標を併用**: 文脈再現率は分散ゼロなので少ないnでも比較できる。
   ただし上限の指標であって検出率そのものではない（前回指摘のとおり一部は定義上の同義）

見積り: X クラス30件 × 2アーム × 3反復 = 180ラン ≈ **$70〜90**、実時間 3〜4時間。
社内リポの過去PRから見逃し事例を書き起こせば、同じ枠組みで社内の数字が出る。

### 導入判断（暫定）

- **今すぐ全社導入する根拠は無い**（品質の優位が測れていない、コストは +49%）
- **切り捨てる根拠も無い**（差がないことは示せていない）
- 予算上限に対しては、どちらの構成でも桁が違う（200PR/月で $78 vs $115）。
  **判断軸はコストではなく品質**であり、その品質差はまだ測れていない
- 入れて試す場合は `impact` を **depth 1・CLI 経由**、`callers_of` の併用は
  `import_style.py` で B率を測ってから
