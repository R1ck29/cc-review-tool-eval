FINDING: app/pricing.py | `compute_total` now takes a required third parameter `tax_rate`, but its only caller `app/orders.py:create_order` still calls `pricing.compute_total(quantity, unit_cents)`, so every order creation through `/orders` raises `TypeError: compute_total() missing 1 required positional argument`.
FINDING: app/pricing.py | `int(...)` truncates toward zero in both `apply_bulk_discount` and `compute_total`, systematically under-charging by up to a cent per line (e.g. `unit_cents=111, quantity=11` → `1098.9` → `1098`); use `round()` or exact integer arithmetic (`unit_cents * quantity * 9 // 10`) for money.
FINDING: app/pricing.py | Discounted and undiscounted branches of `apply_bulk_discount` return different types/precision — the discounted branch returns a truncated `int` while the fallthrough returns `unit_cents * quantity` unconverted (a float if `unit_cents` is a float), so downstream integer-cents assumptions break inconsistently depending on quantity.
FINDING: app/pricing.py | `get("BULK_THRESHOLD")` has no default and no None check, so a missing/mistyped config key makes `quantity > None` raise `TypeError` instead of falling back to a safe no-discount path.
FINDING: app/pricing.py | The 10% discount rate is a hardcoded magic number (`0.9`) while the threshold is configurable, so the discount cannot be tuned via `SETTINGS` and the two halves of the rule can drift apart.
FINDING: app/pricing.py | No validation of inputs: negative or zero `quantity`, negative `unit_cents`, or a `tax_rate` expressed as a percentage (e.g. `8.5` meaning 8.5%) silently produce absurd totals — `compute_total(1, 100, 8.5)` returns `950` cents.
FINDING: app/pricing.py | Pricing ignores the per-order discount that the domain already models (`Order.discount_percent`, `orders.discount_percent` column), so any customer/order-level discount is silently dropped from the computed total.
