I've reviewed `app/utils.py` against the rest of the service. Both helpers are new and currently uncalled (`grep` finds no importers), so all findings are intrinsic to the change plus the risk they carry for future callers.

**Key issue:** `parse_money` does binary-float arithmetic and then truncates with `int()`. Many exact-cent decimal strings are not representable as doubles and land *just below* the target integer, so the result is one cent short. `float("4.35") * 100` is `434.99999999999994` → `434`; `float("8.20") * 100` is `819.9999999999999` → `819`. For a function whose entire contract is "parse into integer cents," this silently loses money on a large class of ordinary inputs. The fix is `Decimal(raw).scaleb(2)` with an explicit quantize/rounding mode (or at minimum `round()` instead of `int()`, which narrows but does not eliminate the problem).

Note that the docstring's own example is fine (`12.34` → `1234`), which makes the defect easy to miss in a spot check — the failure depends on the specific decimal.

FINDING: app/utils.py | `parse_money` truncates a binary float with `int()`, so decimals that round down in IEEE-754 lose a cent — `parse_money("4.35")` returns 434 and `parse_money("8.20")` returns 819 instead of 435 and 820.
FINDING: app/utils.py | `int()` truncates toward zero rather than to nearest, so sub-cent precision is silently discarded instead of rejected or rounded — `parse_money("0.999")` returns 99, not 100.
FINDING: app/utils.py | Truncation toward zero is asymmetric across signs, so a refund and a charge of the same magnitude do not cancel — `parse_money("0.019")` returns 1 while `parse_money("-0.019")` returns -1 relative to a floor-rounding ledger, leaving reconciliation off by a cent.
FINDING: app/utils.py | `parse_money` performs no input validation and lets `float()` raise, so a malformed API amount such as `"$12.34"`, `"1,234.56"`, or `""` propagates an uncaught `ValueError` (and `None` a `TypeError`) to the caller as a 500 rather than a clean 400-style validation error.
FINDING: app/utils.py | `parse_money` accepts non-finite input because `float()` parses `"inf"`/`"nan"`, then fails inside `int()` with a different exception type per case — `OverflowError` for `"inf"` and `ValueError` for `"nan"` — making uniform error handling at the call site impossible.
FINDING: app/utils.py | `float()` silently accepts PEP 515 underscore separators and surrounding whitespace, so clearly malformed amounts like `"1_000.00"` parse as 100000 cents instead of being rejected.
FINDING: app/utils.py | `clamp` silently returns `low` when callers pass inverted bounds (`clamp(5, 10, 0)` returns 10, which violates the `high` bound) instead of asserting or raising on `low > high`.
FINDING: app/utils.py | `clamp` does not handle NaN: because `min`/`max` return their first argument on a false comparison, `clamp(float("nan"), 0, 10)` silently yields 10, converting a NaN into a plausible-looking boundary value rather than propagating the error.
FINDING: app/utils.py | Neither `parse_money` nor `clamp` has type annotations, and `clamp` has no docstring, contrary to the project's Python style rule requiring annotations on all function signatures.
FINDING: app/utils.py | The new helpers ship with no unit tests (`tests/` contains only `test_pricing.py`) and no call sites anywhere in `app/`, so the rounding contract is unverified and the module is currently dead code.
