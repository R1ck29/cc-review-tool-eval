## Review of `app/models.py` (with surrounding context)

The change renames/introduces `Order.discount_percent`, and that name is not what the rest of the service reads. That is the highest-severity issue; the remaining findings are other correctness problems visible in the provided files.

FINDING: app/models.py | `Order` exposes the discount as `discount_percent`, but `serializers.order_to_dict` reads `order.discount`, so every serialization of an order raises `AttributeError: 'Order' object has no attribute 'discount'`.
FINDING: app/serializers.py | `order_to_dict` accesses the non-existent attribute `order.discount` instead of `order.discount_percent`, and the output key `"discount"` also silently changes the wire contract's meaning (raw discount vs. percent).
FINDING: app/models.py | `Order` is constructed positionally via `Order(*row)` in `repository.get_order`, so the field order is an implicit contract with the `SELECT` column list in `db.fetch_order_row`; any reorder/rename on either side mis-assigns values silently rather than failing.
FINDING: app/models.py | `discount_percent: float` has no default while the DB column is `discount_percent REAL DEFAULT 0.0` (nullable), so a `NULL` discount is passed straight through as `None` into a field annotated `float`, and no callers can construct an `Order` without supplying it.
FINDING: app/models.py | The unit of `discount_percent` is undefined (0–100 vs 0.0–1.0) and no code ever reads it — `pricing.apply_bulk_discount` hardcodes `0.9` instead of using the order's stored discount, so the persisted discount has no effect on any total.
FINDING: app/models.py | The `Customer` dataclass is dead code: nothing in the repository, serializers, or services constructs or consumes it, and it has no linkage to `Order.customer_id`.
FINDING: app/models.py | Dataclasses are mutable and unvalidated (not `frozen=True`, no `__post_init__` checks), so a domain `Order` can hold a negative `total_cents`, an out-of-range `discount_percent`, or an arbitrary `status` string not in the known status set.
FINDING: app/db.py | The query selects `discount_pct`, but `schema.sql` defines the column as `discount_percent`, so `fetch_order_row` raises `sqlite3.OperationalError: no such column: discount_pct` for every lookup.
FINDING: app/pricing.py | `compute_total` requires a third parameter `tax_rate`, but `orders.create_order` calls `pricing.compute_total(quantity, unit_cents)` with two arguments, raising `TypeError` on every order creation.
FINDING: app/pricing.py | `apply_bulk_discount` uses `quantity > threshold` while its docstring says the discount applies when the order "reaches" `BULK_THRESHOLD`, an off-by-one that makes `tests/test_pricing.py::test_bulk_discount_applies_at_threshold` fail (returns 1000, expects 900).
FINDING: app/pricing.py | The discounted branch truncates with `int(...)` while the non-discounted branch returns a raw product, so the return type is inconsistent (float/int) and money is floored rather than rounded, losing up to a cent per line.
FINDING: app/pricing.py | `compute_total` applies tax to the discounted subtotal with `int(...)` truncation and no validation that `tax_rate` is non-negative or is a rate rather than a percentage.
FINDING: app/repository.py | With `MAX_RETRIES = 0` the loop runs exactly once, and even when >0 it retries the identical query with no backoff and no exception handling — a `sqlite3` error propagates immediately, so the "retry" is a no-op for every realistic failure mode.
FINDING: app/orders.py | `get_order_summary` dereferences `order.id` without checking for `None`, so a missing order id turns `repository.get_order`'s `None` return into `AttributeError` instead of a not-found result.
FINDING: app/orders.py | `_normalise` assigns to a local variable named `STATUS_OPEN`, shadowing the module-level constant; the function works by accident but reads as if it mutates the constant, and it is never called anywhere.
FINDING: app/orders.py | `create_order` returns a plain dict with no `id` and no `discount_percent`, so it is not the `Order` model the rest of the stack (serializers, repository) expects and nothing is ever persisted.
FINDING: app/events.py | `publish_order_created` publishes on `DEFAULT_TOPIC` (`"order.created"`) while `handlers.py` subscribes to `"order_created"`, so the handler is never invoked — a silent no-op because `publish` ignores unknown topics.
FINDING: app/events.py | `publish` runs subscribers synchronously with no error isolation, so one raising subscriber aborts delivery to all later subscribers of the same topic.
FINDING: app/tasks.py | `run_task` builds an attribute name from caller-supplied `name` and `getattr`s it off the `handlers` module, so a name like `"order_created"` works but any imported symbol matching the prefix is callable as a task, and `LookupError(fn_name)` loses the original task name in its message.
FINDING: app/utils.py | `parse_money` uses binary float arithmetic then truncates, so `parse_money("12.34")` returns 1233 instead of 1234; it needs `Decimal` or rounding.
FINDING: app/utils.py | `clamp` silently returns `low` when `low > high` instead of rejecting an inverted range.
FINDING: app/db.py | `connect()`/`fetch_order_row` never use a context manager, so the connection leaks if `cur.execute` or `fetchone` raises, and a new connection is opened per query with no pooling.
FINDING: app/api.py | `create` reads mixed-convention keys (`customerId` vs `quantity`/`unit_cents`) directly with `[]`, so any missing field raises an unhandled `KeyError` rather than a 400-style response, and no type/range validation is done on `quantity` or `unit_cents`.
FINDING: app/api.py | The `route` decorator keys `ROUTES` by path only, ignoring HTTP method and silently overwriting a previously registered handler for the same path.
FINDING: tests/test_pricing.py | Coverage is limited to a single bulk-discount case; there is no test for `compute_total`, the repository/model mapping, or serialization — which is why the `discount` → `discount_percent` rename breaks at runtime rather than in CI.
