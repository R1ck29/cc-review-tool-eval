No file-reading tools are available in this session, so this is a static review of the source as given. Note that `app/config.py` was referenced as context but its contents were not actually included, so findings about `get("BULK_THRESHOLD")`'s return value are stated as unverified risks.

FINDING: app/pricing.py | Off-by-one in the discount boundary: the docstring says the discount applies when the order "reaches" BULK_THRESHOLD, but `quantity > threshold` skips the discount at exactly the threshold quantity, so an order of exactly BULK_THRESHOLD units is overcharged.
FINDING: app/pricing.py | `int(unit_cents * quantity * 0.9)` truncates toward zero instead of rounding, so the discounted subtotal is systematically rounded down (up to 1 cent lost per line in the customer's favor) rather than rounded to nearest cent.
FINDING: app/pricing.py | `int(subtotal * (1 + tax_rate))` truncates the tax amount downward, systematically under-collecting tax by up to a cent per line and producing totals that won't reconcile with a tax authority's rounding rules.
FINDING: app/pricing.py | Truncation is applied twice (once in `apply_bulk_discount`, again in `compute_total`), compounding the downward bias so a single discounted, taxed line can lose ~2 cents versus a single rounding at the end.
FINDING: app/pricing.py | Money is computed with binary floating point (`* 0.9`, `* (1 + tax_rate)`), so representation error combined with `int()` truncation can drop a full cent when a product lands just below an integer (e.g. a true value of 270 computed as 269.99999999999994 becomes 269).
FINDING: app/pricing.py | `apply_bulk_discount` has an inconsistent return type: the discount branch returns `int` while the non-discount branch returns `unit_cents * quantity` unconverted, so float or Decimal inputs yield a non-integer cents value from one path only.
FINDING: app/pricing.py | The result of `get("BULK_THRESHOLD")` is used directly in a comparison with no type coercion or default, so a `None` or string value from config (common for env-backed settings) raises `TypeError: '>' not supported between instances of 'int' and 'NoneType'/'str'` inside the pricing path.
FINDING: app/pricing.py | The config lookup is performed on every call rather than resolved once, so a threshold change between calls can price two lines of the same order under different rules, and it puts an uncached config read in a hot path.
FINDING: app/pricing.py | Neither function validates its inputs: negative or zero `quantity`, negative `unit_cents`, or `None` are accepted silently and produce negative/zero totals instead of raising.
FINDING: app/pricing.py | For negative amounts (refunds, credit lines) `int()` truncates toward zero rather than down, so refunds round in the opposite direction from charges, creating an asymmetric rounding bias between debits and credits.
FINDING: app/pricing.py | `tax_rate` is unvalidated and its unit is undocumented, so a caller passing a percentage (e.g. `8.5` instead of `0.085`) silently inflates the total ~9x, and a negative rate silently reduces it.
FINDING: app/pricing.py | The 10% discount is a hardcoded magic number (`0.9`) even though the threshold that triggers it is configurable, so the discount rate cannot be changed without a code deploy and is not mentioned in the docstring.
FINDING: app/pricing.py | No tests accompany the change, in particular none pinning the discount boundary (`quantity == threshold`, `threshold ± 1`) or the rounding behavior, which is exactly where the off-by-one and truncation defects live.
