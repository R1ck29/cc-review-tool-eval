Reviewed `app/db.py` against the schema and its callers.

FINDING: app/db.py | The SELECT reads `discount_pct`, but the column in `schema.sql` is named `discount_percent`, so every call to `fetch_order_row` raises `sqlite3.OperationalError: no such column: discount_pct` and no order can ever be loaded.
FINDING: app/db.py | The connection is closed only on the success path — if `cur.execute()` or `fetchone()` raises (e.g. the bad column name above), `conn.close()` is skipped and the sqlite connection/file handle leaks, so repeated failures exhaust handles.
FINDING: app/db.py | `sqlite3.connect()` silently creates an empty database file when `DB_PATH` does not exist, so a misconfigured path fails later with a confusing "no such table: orders" instead of a clear startup error.
FINDING: app/db.py | `DB_PATH` is a bare relative filename, so the database resolved depends on the process working directory and different callers can silently read different files.
FINDING: app/db.py | `connect()` opens a brand-new connection on every row fetch with no pooling, reuse, or `timeout`/isolation configuration, which is wasteful under the retry loop in `repository.get_order` and offers no protection against `database is locked`.
FINDING: app/db.py | The function returns a bare positional tuple that `repository.get_order` splats into `Order(*row)`, so any reordering or addition of columns in this SELECT silently maps values into the wrong dataclass fields instead of failing; a `row_factory` or explicit mapping would make the contract safe.
FINDING: app/db.py | No exception handling around the sqlite calls at all: `sqlite3.Error` propagates raw database errors up through the repository into the HTTP layer.
FINDING: app/db.py | If `DB_PATH` is missing from `SETTINGS`, `get()` returns `None` and `sqlite3.connect(None)` raises an opaque `TypeError` rather than a configuration error.
FINDING: app/pricing.py | `compute_total` requires a `tax_rate` argument but `orders.create_order` calls it with only two arguments, so every order creation raises `TypeError: compute_total() missing 1 required positional argument`.
FINDING: app/pricing.py | `apply_bulk_discount` uses `quantity > threshold` while its docstring says the discount applies when the order *reaches* the threshold — an off-by-one that makes `tests/test_pricing.py::test_bulk_discount_applies_at_threshold` fail (returns 1000, expects 900).
FINDING: app/serializers.py | `order_to_dict` reads `order.discount`, but the `Order` dataclass field is `discount_percent`, so serialization raises `AttributeError` for every order.
FINDING: app/handlers.py | The handler subscribes to the topic `"order_created"` while `events.publish_order_created` publishes to `DEFAULT_TOPIC` (`"order.created"`), so the handler is never invoked and order-created events are silently dropped.
FINDING: app/repository.py | `get_order` can return `None`, but `orders.get_order_summary` immediately dereferences `order.id`, raising `AttributeError: 'NoneType' object has no attribute 'id'` for a missing order id.
FINDING: app/repository.py | With `MAX_RETRIES` set to 0 the loop runs exactly once, so the documented retry behaviour is a no-op; worse, the loop only retries the "row not found" case (which is deterministic and will never change) and does not retry actual database errors, and it has no backoff.
FINDING: app/repository.py | `get("MAX_RETRIES") + 1` raises `TypeError` if the key is ever absent, since `config.get` returns `None` by default rather than a numeric fallback.
FINDING: app/utils.py | `parse_money` truncates instead of rounding, so float representation error makes `parse_money("12.34")` return 1233 cents rather than 1234; it should use `round()` or `Decimal`.
FINDING: app/orders.py | `_normalise` rebinds the module-level constant name `STATUS_OPEN` as a local variable, shadowing the constant and making the function misleading/dead-code-prone (and it is never called anywhere).
FINDING: app/api.py | `create` indexes `payload["customerId"]`, `payload["quantity"]`, and `payload["unit_cents"]` with no validation or error handling, so a malformed request raises an unhandled `KeyError`; the mixed camelCase/snake_case keys also suggest at least one key name is wrong.
FINDING: app/orders.py | `create_order` never persists the order and returns a dict with no `id`, so the API response cannot be correlated with any stored record.
FINDING: app/events.py | `publish` invokes subscribers with no exception isolation, so one failing subscriber prevents all later subscribers on the same topic from running.
FINDING: app/tasks.py | `run_task` resolves handlers via `getattr` on the whole `handlers` module using caller-supplied `name`, which allows dispatch to any module attribute matching the prefix and raises `TypeError` rather than `LookupError` if the resolved attribute is not callable.
