Reviewed `app/models.py` against its consumers. The dominant issue is the `discount` → `discount_percent` field name, which no caller was updated for.

FINDING: app/models.py | `Order.discount_percent` does not match the `order.discount` attribute read by `app/serializers.py:order_to_dict`, so every serialization call raises `AttributeError` at runtime.
FINDING: app/serializers.py | `order_to_dict` reads the now-nonexistent `order.discount` and emits it under the key `"discount"`, so even after a rename the wire format still advertises a bare "discount" while carrying a percent value — a silent unit/semantics change for API clients.
FINDING: app/models.py | The rename from `discount` to `discount_percent` implies a unit change (fraction vs. percent) but nothing in the model documents, validates, or converts it, so `0.2` and `20` are both accepted and mean opposite things to different callers.
FINDING: app/models.py | `discount_percent` has no bounds validation (`__post_init__` or otherwise), so negative or >100 discounts are constructible and would produce negative/inflated order totals downstream.
FINDING: app/models.py | The dataclass relies entirely on positional field order because `app/repository.py` builds it via `Order(*row)`; inserting, reordering, or removing a field silently mis-assigns DB columns (e.g. `status` receiving a discount value) with no type error, and there is no `from_row` classmethod or keyword construction to guard it.
FINDING: app/models.py | `Order` has five required fields and no defaults, so any DB row with a differing column count raises a bare `TypeError` from `Order(*row)` in the repository rather than a diagnosable schema error.
FINDING: app/models.py | Type annotations are not enforced at runtime by `@dataclass`, so `total_cents` can be populated with a float/str/`None` straight from the DB row and only fail much later during arithmetic or serialization.
FINDING: app/models.py | `status` is an unconstrained `str` with no `Enum` or allowed-value check, so typos like `"complete"` vs `"completed"` propagate silently through comparisons.
FINDING: app/models.py | `Order` and `Customer` are mutable (not `frozen=True`), so repository-returned models can be mutated in place by callers, and because `eq=True` sets `__hash__` to `None` they cannot be used in sets or as dict keys.
FINDING: app/models.py | `Order.customer_id` is an untyped `int` with no relationship to `Customer` and no validation, so orphaned orders referencing a nonexistent customer are representable.
FINDING: app/models.py | `Customer` is defined but never constructed or referenced by any module in this change (repository/serializers only handle `Order`), suggesting dead code or a missing loader/serializer for it.
FINDING: app/repository.py | `MAX_RETRIES` is `0` in `app/config.py`, so `attempts = 1` and the documented "retrying per MAX_RETRIES" loop never actually retries.
FINDING: app/repository.py | The retry loop only re-runs when `row` is falsy — i.e. when the order genuinely does not exist — so it burns attempts on a deterministic miss while transient `db.fetch_order_row` exceptions propagate immediately without any retry or backoff.
FINDING: app/repository.py | `get("MAX_RETRIES") + 1` will raise `TypeError: unsupported operand type(s) for +: 'NoneType' and 'int'` if the key is ever absent, because `config.get` returns `None` by default instead of a numeric fallback.
FINDING: app/repository.py | `from app import db` refers to a module not present in the package (`app/__init__.py` is empty and no `app/db.py` exists in the change), which would fail at import time.
