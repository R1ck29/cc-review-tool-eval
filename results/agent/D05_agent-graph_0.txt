## Review of `app/pricing.py`

Graph analysis: the change touches `apply_bulk_discount` and `compute_total`; blast radius reaches `app/orders.py::create_order` (only caller of `compute_total`) and `tests/test_pricing.py` (only test of `apply_bulk_discount`). Both are broken by the change.

FINDING: app/pricing.py | `compute_total` gained a required third parameter `tax_rate`, but its only caller `app/orders.py:8` still calls `pricing.compute_total(quantity, unit_cents)`, so every order creation raises `TypeError: compute_total() missing 1 required positional argument: 'tax_rate'`.
FINDING: app/orders.py | `create_order` (line 8) invokes `pricing.compute_total` with two arguments and has no `tax_rate` to supply, so it must be updated (or `tax_rate` given a default) or the order path is dead.
FINDING: app/pricing.py | The threshold comparison `quantity > threshold` (line 8) contradicts the docstring "when the order reaches BULK_THRESHOLD units" — it is an off-by-one that skips the discount exactly at the threshold, where `>=` is intended.
FINDING: tests/test_pricing.py | `test_bulk_discount_applies_at_threshold` asserts `apply_bulk_discount(10, 100) == 900` but with `BULK_THRESHOLD=10` and the strict `>` comparison the call now returns 1000, so the existing test fails.
FINDING: app/pricing.py | `get("BULK_THRESHOLD")` (line 7) passes no default, so if the key is ever absent/removed from `SETTINGS` the function gets `None` and `quantity > None` raises `TypeError: '>' not supported between instances of 'int' and 'NoneType'` instead of degrading to the undiscounted price.
FINDING: app/pricing.py | The discount multiplies by the float literal `0.9` and truncates with `int()` rather than rounding, so monetary results are biased down and can be a cent off (e.g. `apply_bulk_discount(11, 33)` → `int(326.70000000000005)`-style truncation), which is inconsistent with the integer-cents convention used by `app/utils.py::parse_money`.
FINDING: app/pricing.py | `apply_bulk_discount` returns an `int` on the discounted branch (line 9) but returns the raw `unit_cents * quantity` on the other branch (line 10), so a float `unit_cents` yields a float total — an inconsistent return type that then propagates into `compute_total`.
FINDING: app/pricing.py | `compute_total` truncates with `int(subtotal * (1 + tax_rate))` instead of rounding, systematically undercharging tax by up to one cent per line; `round()` (or `Decimal`) is the correct money operation.
FINDING: app/pricing.py | Neither the hard-coded `0.9` discount factor nor `tax_rate` is validated (negative `tax_rate`, `tax_rate` supplied as a percentage like `8.5` instead of `0.085`, or negative `quantity`) — all silently produce nonsense totals, and negative quantity even triggers the discount branch inversely.
FINDING: app/pricing.py | The magic `0.9` discount rate is hard-coded while its companion `BULK_THRESHOLD` is configurable via `app.config`, an inconsistency that makes the discount rate un-tunable and easy to drift from business rules.
FINDING: tests/test_pricing.py | There is no test covering `compute_total` at all, so the new `tax_rate` parameter, its interaction with the discount, and the broken call in `app/orders.py` are entirely uncovered.
FINDING: app/pricing.py | The changed function signatures carry no type annotations (`quantity`, `unit_cents`, `tax_rate`, return types), so the int-cents-vs-float contract that the truncation bugs hinge on is unenforced.
