# はじめに読む — Claude Code / Codex のトークン代を下げる

前提知識ゼロ向け。**15分**で終わります。

---

## 3行まとめ

1. ツールを増やしても安くなりません。**増やすと高くなります**
2. 安くなるのは **「重い呼び方をやめる」** ことだけ
3. やることは **設定ファイル2つを編集するだけ**

---

## 配るもの / 配らないもの

**このリポジトリ（`cc_review_tool_eval`）を社内に配る必要はありません。**
評価の根拠であって、実行に必要な部品ではないからです。

| | 中身 | 誰が |
|---|---|---|
| **必須** | `~/.mcp.json` の2行 ＋ `uv tool install` 1回 ＋ `CLAUDE.md` に貼るブロック | **全員** |
| 任意 | `harness/measure_savings.py`（効果の実測） | 導入を決める人が**1回だけ** |
| 任意 | `harness/string_contracts.py`（RULE 4） | 精度を確認してから。無くても RULE 1–3 は動く |
| 不要 | `bench/` `results/` `docs/` | 根拠。読みたい人だけ |

**削減そのものを起こしているのは `CLAUDE.md` のブロックだけです。**
他はすべて「壊れないようにする」「効果を確かめる」ための付属品です。

---

## そもそも何にお金がかかっているのか

Claude Code や Codex は、質問のたびに**コードをコンテキストに読み込みます**。
このコンテキストの量がそのまま料金です。

`code-review-graph` のようなツールは「必要なファイルだけ選ぶ」ことでこれを減らします。
ただし **選び方の設定を間違えると、全部読むより高くなります。**

実測例（変更ファイル1つに対して）:

```
get_impact_radius_tool を既定で1回呼ぶ    →  80,353 トークン
これ1回で、レビュー文脈まるごとの 4.2倍
```

**このツールには出力を小さくする設定が存在しません**（後述）。だから避けるしかない。
ここが最大のポイントです。

## やること（コピペで完了）

### ステップ1 — バージョンを固定する

`~/.mcp.json` を開いて、`args` をこう書き換えます。

```json
{
  "mcpServers": {
    "code-review-graph": {
      "command": "uvx",
      "args": ["--from", "code-review-graph==2.3.8", "code-review-graph", "serve"],
      "type": "stdio"
    }
  }
}
```

**なぜ**: `uvx code-review-graph` と書くと毎回**最新版を勝手に取ってきます**。
実際このプロジェクトでは、検証したのは 2.3.7 なのに動いていたのは 2.3.8 でした。
2.3.8 では欠陥の検出率が落ちる変更が入っていました（56% → 44%）。

### ステップ2 — 書き込む側のバージョンも合わせる

```bash
uv tool install code-review-graph==2.3.8 --force
```

**なぜ**: ファイル保存のたびに動くフックは、`~/.mcp.json` ではなく **PATH 上のコマンド**を使います。
つまり**グラフを書く側と読む側が別バージョン**になり得ます。実際なっていました。
（スキーマは同一で、2.3.8 は 2.3.7 のデータを問題なく更新できることは確認済みです）

### ステップ3 — モデルに呼び方を教える

`~/.claude/CLAUDE.md`（全プロジェクト共通）か、
プロジェクト直下の `CLAUDE.md` に、以下をそのまま貼ります。

```markdown
## code-review-graph の呼び方（コスト管理）

**RULE 1（削減の大部分）— `get_impact_radius_tool` を既定設定で呼ばない。**
変更ファイル1つで 80,353 トークン。上限を掛ける手段が存在しない
（`max_results` は渡すとエラー、`max_depth=1` は1%しか減らない、
環境変数 `CRG_MAX_IMPACT_NODES` / `CRG_MAX_IMPACT_DEPTH` は無効）。
トリアージには `detail_level="minimal"`（213トークン）を使う。
ただし minimal は件数とリスク値だけで**影響ファイル名を返さない**ので、
レビュー文脈としては使えない。

**RULE 2 — レビュー文脈は `get_review_context_tool` から取り、
必ず `max_results=25` と `max_depth=1` を渡す。**
再現率は変わらないことを12欠陥のベンチで確認済み。渡して損はない。

**RULE 3（品質・約900トークン）— グラフの文脈だけを信用しない。**
変更されたシンボルに対して `query_graph_tool` の `pattern="callers_of"` を必ず併用する。
これがないと実害欠陥の検出率が 44% にとどまり、併用すると 78% に戻る。

**RULE 4（品質・0トークン・任意）— 文字列契約の事前チェックが使える場合は回す。**
コードグラフに原理的に映らない欠陥（SQLのカラム名、イベント名、dictのキー）を拾う。
参照実装は `cc_review_tool_eval` リポジトリ内の `harness/string_contracts.py`。
**グローバルには入らないので、そのファイルが無い環境ではこのルールは飛ばすこと**
（エラーとして報告しない）。

RULE 1〜3 は MCP サーバだけに依存するのでどこでも効く。RULE 4 だけは環境依存。
```

**RULE 4 を使わないなら、その行ごと削除して構いません。** RULE 1〜3 が削減の本体です。

### ステップ4 — Claude Code を再起動

`~/.mcp.json` の変更は再起動後に反映されます。

## （任意）効果を自分のリポで測る

**ここから先は導入に必須ではありません。** 上の4ステップで削減はもう効いています。

これは「本当に効いているのか」を確かめたい人と、導入を決める立場の人が
**1回だけ**使うツールです。全員に配る必要はありません。
LLMは呼ばずローカルのMCPサーバを叩くだけなので、**API課金はゼロ**です。

**他人の数字を信じないでください。効果はファイルサイズに強く依存します。**

```bash
# まだグラフが無ければ作る（初回だけ）
code-review-graph build --repo /path/to/your/repo

# 効果を測る
python harness/measure_savings.py /path/to/your/repo
```

こう出ます:

```
changed file                                     before      after   saved
--------------------------------------------------------------------------
code_review_graph/postprocessing.py              22,644     10,154    2.2x
code_review_graph/tools/review.py                 4,178      4,178    1.0x
--------------------------------------------------------------------------
MEAN get_review_context                           8,133      5,400    1.5x

--- what this means per review ---
  RULE 1  avoid get_impact_radius at default   saves     8,631 tokens/call
  RULE 2  max_results=25, max_depth=1          saves     2,733 tokens/call
  RULE 3  add callers_of                       costs ~     900 tokens (recall 44%->78%)
  RULE 4  string_contracts.py pre-pass         costs         0 tokens

  recommended context per review: ~6,568 tokens
  unparameterised, calling both:  ~16,763 tokens (3x more)
```

**`1.0x` と出ても失敗ではありません。** そのファイルが小さくて上限に達していないだけです。
渡してもコストはゼロなので、そのまま渡してください。

### どういう時にどのくらい削減できるのか

**答え: 変更されたファイルが大きいほど効きます。** リポジトリの規模ではありません。

同じリポジトリ（192ファイル）で、変更ファイルのサイズ別に15件測った実測値：

| 変更ファイル | 既定の合計 | 推奨の合計 | 削減 | 1回あたり節約 |
|---|---|---|---|---|
| 小（~1,000トークン / 約40行） | 4,417 | 3,614 | **1.2x** | 803 |
| 中（1,000〜3,000 / 40〜120行） | 12,997 | 6,364 | **2.0x** | 6,634 |
| 大（3,000〜8,000 / 120〜320行） | 35,385 | 9,794 | **3.6x** | 25,591 |
| 特大（8,000〜 / 320行〜） | 208,613 | 13,365 | **15.6x** | 195,248 |

内訳（どちらのルールが効くか）：

| 変更ファイル | RULE 1 が回避する `impact` | RULE 2 の削減 |
|---|---|---|
| 小 | 1,971 | 1.0x（上限に届かない） |
| 中 | 5,606 | 1.4x |
| 大 | 18,958 | 1.9x |
| 特大 | **173,892** | 2.8x |

**大きいファイルを触るときほど桁違いに効きます。** 小さいファイルでは 1.2倍程度ですが、
そもそも絶対額が小さいので気にする必要がありません。

### 最悪ケース

`parser.py`（161,295トークンの巨大ファイル）を変更したとき、
`get_impact_radius_tool` を既定で1回呼ぶと **392,999トークン**。

**どのコンテキストウィンドウにも入りません。1回でセッションが破綻します。**
RULE 1 はコスト対策であると同時に、**事故防止**でもあります。

### まとめると

- **普段の小さな修正** → 効果は 1.2倍程度。誤差
- **通常のPR（100〜300行のファイル）** → **2〜3.6倍**
- **大きいファイルやリファクタ** → **15倍以上**、かつ**破綻を防ぐ**

払うものがゼロなので、どのケースでも設定して損はありません。
自分のリポで測りたい場合は下記のスクリプトを使ってください。

## よくある勘違い

| 勘違い | 実際 |
|---|---|
| 「ツールを増やせば賢く・安くなる」 | MCPサーバを足すたび固定費が増えます。4ツール構成は月$345、1ツールで正しく呼べば月$69 |
| 「環境変数で上限を設定できる」 | `CRG_MAX_IMPACT_NODES` などは**完全に無効**です。コードが自前の既定で上書きします |
| 「`detect_changes` がレビュー文脈」 | 102〜268トークンと安いですが、中身は件数とリスク値だけで**コードを1行も含みません** |
| 「`impact` を depth 1 にすれば安い」 | **1%しか減りません**。避ける以外の手がありません |
| 「グラフがあれば見逃さない」 | グラフ単体では実害欠陥の **44%** しか届きません。`callers_of` 併用が必須です |

---

## 効果の内訳（何が効いているか）

| やること | コスト | 効果 |
|---|---|---|
| **RULE 1** `impact` を既定で呼ばない | 0 | **最大の削減**。1回8,631〜80,353トークンを丸ごと回避 |
| **RULE 2** `max_results=25` | 0 | 1.0〜3.3倍（ファイルサイズ次第） |
| **RULE 3** `callers_of` 併用 | +900 | 検出率 44% → **78%** |
| **RULE 4** 文字列プリパス | 0 | グラフに映らない欠陥を拾う |

RULE 1 と 2 は**払うものがゼロ**です。迷う理由がありません。
RULE 3 は 900トークン払って検出率を34ポイント上げる取引で、まず割に合います。

## やってはいけないこと

- **`better-code-review-graph` を入れる** — `GEMINI_API_KEY` / `GOOGLE_API_KEY` /
  `OPENAI_API_KEY` が環境にあるだけで、確認なしに**ソースコード本文を外部に送信**します。
  社外持ち出し禁止の環境では使えません
- **`Graphify` を入れる** — グラフ構築自体がサブエージェント経由＝**構築コストがトークン建て**です
- **MCPサーバを増やす** — Claude Code は遅延ロードがあるので影響は小さいですが、
  **Codex では1リクエストあたり数千トークンの固定費**になります

---

## Codex でも使う場合

Claude Code は遅延ロードが効くので MCP のままで問題ありません（固定費 348トークン）。

**Codex は遅延ロード対応を確認できませんでした。** MCP だと1リクエストあたり
8,895トークン払う可能性があります。Codex を本番で使うなら、MCP をやめて **CLI + skill 方式**にしてください。

- 固定費が **0** になる
- `--max-results 25 --depth 1` を**固定フラグとして強制**できる
  （CLAUDE.md の指示はモデル任せで、強制力がありません）

## 困ったら

| 症状 | 対処 |
|---|---|
| `No graph at .../.code-review-graph` | `code-review-graph build --repo <path>` を先に実行 |
| `measure_savings.py` が全部 ERROR | グラフのビルド時とパスが違う可能性。`code-review-graph status --repo <path>` で確認 |
| 指摘が少なすぎる | `string_contracts.py` の WARNING を確認。古い Python だと一部ファイルが走査対象から外れます |
| フックが動かない | フックは git リポジトリ内でのみ動作します（`update` が git diff 駆動のため） |
