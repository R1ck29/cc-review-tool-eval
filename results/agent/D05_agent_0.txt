I've reviewed `app/pricing.py` and traced its callers and config dependencies.

**Findings:**

FINDING: app/orders.py | `create_order` calls `pricing.compute_total(quantity, unit_cents)` with two arguments, but `compute_total` now requires a third `tax_rate` parameter, so every order creation (including the `POST /orders` route in `app/api.py`) raises `TypeError: compute_total() missing 1 required positional argument: 'tax_rate'`.

FINDING: app/pricing.py | `compute_total` added the `tax_rate` parameter with no default value, silently breaking backward compatibility for all existing callers of this public function instead of defaulting to `0`.

FINDING: app/pricing.py | Off-by-one in the threshold check: the docstring says the discount applies "when the order reaches BULK_THRESHOLD units" but `quantity > threshold` only discounts above it, so an order of exactly 10 units gets no discount.

FINDING: tests/test_pricing.py | The existing test `test_bulk_discount_applies_at_threshold` asserts `apply_bulk_discount(10, 100) == 900` but the code returns `1000` at the threshold, so the change leaves the test suite failing.

FINDING: app/pricing.py | `int(unit_cents * quantity * 0.9)` truncates toward zero instead of rounding, so e.g. quantity=15, unit_cents=101 yields 1363 instead of the correctly rounded 1364 cents, systematically under-charging by up to a cent on every discounted line.

FINDING: app/pricing.py | `int(subtotal * (1 + tax_rate))` truncates the tax instead of rounding, so e.g. subtotal=999 with tax_rate=0.1 yields 1098 rather than 1099 cents.

FINDING: app/pricing.py | Discount and tax are computed with binary floating point (`0.9`, `1 + tax_rate`) rather than integer/`Decimal` arithmetic, so representation error combined with truncation can produce a total one cent below the exact value and makes results non-reproducible across inputs.

FINDING: app/pricing.py | `apply_bulk_discount` returns `int(...)` on the discounted path but the raw `unit_cents * quantity` on the non-discounted path, so the return type/precision is inconsistent (a float `unit_cents` leaks a fractional-cent total through `compute_total`).

FINDING: app/pricing.py | `get("BULK_THRESHOLD")` falls back to `None` when the key is absent from `SETTINGS`, and `quantity > None` raises `TypeError` in Python 3 instead of degrading to a sane default such as `get("BULK_THRESHOLD", 10)`.

FINDING: app/pricing.py | The threshold is read from config but the 10% discount rate is a hardcoded magic `0.9`, so the discount amount cannot be configured or tested independently of the threshold.

FINDING: app/pricing.py | No validation of inputs: negative `quantity`, negative `tax_rate`, or `None` produce silently wrong totals (e.g. a negative quantity above the threshold yields a negative "discounted" total) rather than an explicit error.

FINDING: app/pricing.py | The bulk discount is applied to the entire order rather than only to the units above `BULK_THRESHOLD`, which is a plausible misreading of "bulk discount" semantics and is worth confirming against the pricing spec.

FINDING: app/pricing.py | `compute_total` ignores the per-order `discount_percent` field defined on `Order` in `app/models.py`, so customer-specific discounts are never reflected in the computed total.
