I reviewed `app/db.py` together with its full call chain (`repository.py` → `orders.py` / `serializers.py`) and the `schema.sql` it queries.

FINDING: app/db.py | The SELECT queries a column named `discount_pct`, but `schema.sql` defines the column as `discount_percent`, so every call to `fetch_order_row` raises `sqlite3.OperationalError: no such column: discount_pct`.
FINDING: app/db.py | `conn.close()` is only reached on the success path — if `cur.execute`/`fetchone` raises (which it always does here, due to the bad column name), the connection is leaked instead of being closed via `try/finally` or a `with` block.
FINDING: app/db.py | `connect()` passes `get("DB_PATH")` straight to `sqlite3.connect` with no validation; since `config.get` returns `None` for a missing key, a misconfigured deployment fails with an opaque `TypeError` instead of a clear configuration error.
FINDING: app/db.py | `fetch_order_row` returns a bare positional tuple that `repository.get_order` splats into `Order(*row)`, so the mapping silently depends on the SELECT column order matching the dataclass field order — reordering either one produces wrongly-populated orders rather than an error (no `row_factory`/named mapping is used).
FINDING: app/db.py | A new connection is opened and closed on every single row fetch with no pooling or reuse, which is needlessly expensive under the retry loop in `repository.get_order`.
FINDING: app/db.py | `DB_PATH` defaults to the relative path `orders.db`, so the service silently opens (and SQLite auto-creates) a different empty database depending on the process working directory.
FINDING: app/db.py | Public functions lack the type annotations required by the project's Python style rules, and the documented `-> row | None` contract is only stated in the docstring.
FINDING: app/repository.py | `get_order` retries only when `fetch_order_row` returns a falsy row and does not catch `sqlite3.Error`, so the `MAX_RETRIES` loop cannot mask the transient DB failures it exists for — the `OperationalError` from `db.fetch_order_row` propagates on the first attempt.
FINDING: app/repository.py | The retry loop re-runs an identical deterministic query with no backoff/sleep, so for a genuinely missing order it just performs `MAX_RETRIES + 1` redundant queries before returning `None`.
FINDING: app/repository.py | `Order(*row)` will raise `TypeError` rather than a meaningful error if the number of selected columns ever diverges from the five `Order` fields, and it silently binds the `discount_pct` column to the `discount_percent` field.
FINDING: app/orders.py | `get_order_summary` does not handle the documented `None` return from `repository.get_order`, so a lookup for a nonexistent order id crashes with `AttributeError: 'NoneType' object has no attribute 'id'`.
FINDING: app/serializers.py | `order_to_dict` reads `order.discount`, but the `Order` model populated from `db.fetch_order_row` has the field `discount_percent`, so serializing any order raises `AttributeError`.
