I used the graph to get the blast radius of `app/models.py` (7 files, 11 impacted nodes: `repository.get_order`, `serializers.order_to_dict`, `db.fetch_order_row`, `orders.*`, `pricing.*`), then read each consumer. The change renames the `Order` discount field to `discount_percent` (schema.sql matches), but the two call sites that touch that field were not updated.

FINDING: app/serializers.py | `order_to_dict` still reads `order.discount`, an attribute that no longer exists on the renamed `Order` dataclass field `discount_percent`, so every order serialization raises `AttributeError`.
FINDING: app/db.py | The `fetch_order_row` SELECT still asks for column `discount_pct` while `schema.sql` now declares `discount_percent`, so the query raises `sqlite3.OperationalError: no such column: discount_pct` and no order can ever be loaded.
FINDING: app/models.py | The discount field name is now inconsistent across three layers (`discount_percent` in the model/schema, `discount_pct` in SQL, `discount` on the wire), so the rename silently breaks the persistence and API contracts instead of being a pure refactor.
FINDING: app/models.py | `discount_percent` has no default value while `schema.sql` gives the column `DEFAULT 0.0`, so a row written by SQL defaults still requires an explicit argument at every `Order(...)` construction site and any partial construction raises `TypeError`.
FINDING: app/repository.py | `Order(*row)` builds the model by positional unpacking of the DB row, so any future reorder or insertion of a field in `models.py` (exactly the kind of edit under review) silently assigns wrong values instead of failing loudly.
FINDING: app/serializers.py | Renaming the model field changes the JSON key emitted for the discount (or leaves it stale as `"discount"`), an unversioned breaking change to the wire format for any downstream consumer.
FINDING: app/models.py | The `Customer` dataclass has no callers, constructors, or importers anywhere in the graph, so it is dead code that will drift out of sync with the (nonexistent) customers table.
FINDING: app/orders.py | `create_order` returns a plain dict with only `customer_id`/`total_cents`/`status`, missing `id` and `discount_percent`, so its result is not interchangeable with an `Order` and would blow up if passed to `order_to_dict`.
FINDING: app/orders.py | `pricing.compute_total(quantity, unit_cents)` is called with two arguments but `compute_total` requires a third `tax_rate` parameter, raising `TypeError` on every order creation.
FINDING: app/orders.py | `get_order_summary` dereferences `order.id` without checking for the `None` that `repository.get_order` returns for a missing order, raising `AttributeError` instead of a not-found result.
FINDING: app/repository.py | With `MAX_RETRIES` set to `0` the retry loop runs exactly one attempt with no backoff and no error propagation, contradicting the "retrying per MAX_RETRIES" docstring.
FINDING: app/db.py | `connect()` opens a sqlite connection that is only closed on the success path, so any exception from `cur.execute`/`fetchone` (including the `discount_pct` column error above) leaks the connection.
FINDING: app/pricing.py | `apply_bulk_discount` uses `quantity > threshold` while its docstring and `tests/test_pricing.py` expect the discount at `quantity == threshold`, so the existing test asserting `900` fails (returns `1000`).
FINDING: app/handlers.py | `events.subscribe("order_created", ...)` uses a literal topic that does not match the `DEFAULT_TOPIC` value `"order.created"` used by `publish_order_created`, so the handler is never invoked.
FINDING: app/orders.py | `_normalise` assigns to a local named `STATUS_OPEN`, shadowing the module constant and making the function look like it mutates shared state while actually being a no-op wrapper.
FINDING: app/api.py | The route reads `payload["customerId"]` in camelCase while every other layer uses snake_case keys, and a missing key raises an unhandled `KeyError` rather than a 400-style error.
