I reviewed `app/events.py` against the surrounding modules. The central defect is a topic-string mismatch that silently disables the only subscriber in the system.

FINDING: app/events.py | `publish_order_created` publishes to `DEFAULT_TOPIC` (`"order.created"`, dot-separated) while the only subscriber in `app/handlers.py` registers for `"order_created"` (underscore), so `on_order_created` is never invoked and the event is silently dropped.
FINDING: app/events.py | `publish` silently no-ops when a topic has no subscribers (`_SUBSCRIBERS.get(topic, [])`), so topic typos and wiring mistakes like the one above produce no error, warning, or log and are invisible in production.
FINDING: app/events.py | `publish_order_created` does not import or otherwise guarantee that `app.handlers` has been imported, so delivery depends on some other module (e.g. `app/tasks.py`) having imported it first for its `subscribe(...)` side effect — import order alone can silently disable all handlers.
FINDING: app/events.py | If `DEFAULT_TOPIC` is missing from `SETTINGS`, `get("DEFAULT_TOPIC")` returns `None` and `publish_order_created` publishes to topic `None`, which is a valid dict key and therefore fails silently instead of raising a configuration error.
FINDING: app/events.py | `publish` iterates subscribers with no exception handling, so the first handler that raises aborts the loop and every remaining subscriber for that topic is skipped, with the exception propagating into unrelated caller code.
FINDING: app/events.py | `publish` iterates the live list returned by `_SUBSCRIBERS.get(topic, [])` rather than a copy, so a handler that calls `subscribe()` for the same topic during dispatch mutates the list mid-iteration, causing newly added handlers to run in the same publish (potentially unbounded recursion/looping).
FINDING: app/events.py | `subscribe` performs no duplicate check, so registering the same function twice (e.g. a module imported under two names, or `handlers` re-imported in tests) causes the handler to fire multiple times per event.
FINDING: app/events.py | Handler return values are discarded by `publish`, so `on_order_created`'s `f"handled {payload.get('id')}"` result is unreachable through the event path and only observable via `tasks.run_task`, making the two dispatch paths behave inconsistently.
FINDING: app/events.py | There is no `unsubscribe` or way to clear `_SUBSCRIBERS`, so the module-level global accumulates handlers for the process lifetime and leaks state across tests.
FINDING: app/events.py | `_SUBSCRIBERS` is unsynchronized global mutable state with no thread-safety documentation, so concurrent `subscribe`/`publish` from background tasks can observe a partially updated subscriber list.
FINDING: app/events.py | `subscribe` never validates that `fn` is callable, so a bad registration fails only later inside `publish` with a `TypeError` at an unrelated call site.
FINDING: app/events.py | The payload contract is unenforced and undocumented: handlers assume a dict (`payload.get('id')`), so publishing any non-mapping payload raises `AttributeError` from inside `publish`.
FINDING: app/handlers.py | The topic is hardcoded as the string literal `"order_created"` instead of reusing `config.DEFAULT_TOPIC`/a shared constant, which is the root cause that allowed publisher and subscriber to drift apart.
FINDING: app/config.py | `MAX_RETRIES` is `0`, so `repository.get_order` computes `attempts = 1` and the documented retry behaviour never actually retries.
FINDING: app/repository.py | `get("MAX_RETRIES") + 1` raises `TypeError` if the key is ever absent (since `get` returns `None`), and the retry loop re-queries immediately with no backoff and no distinction between "not found" and "transient failure".
FINDING: app/db.py | `conn.close()` is not in a `try`/`finally`, so any exception from `cur.execute` or `fetchone` leaks the SQLite connection.
FINDING: app/pricing.py | `apply_bulk_discount` uses `quantity > threshold` while its docstring says the discount applies when the order "reaches" `BULK_THRESHOLD`, an off-by-one that denies the discount at exactly 10 units.
FINDING: app/pricing.py | `compute_total` and `apply_bulk_discount` use `int()` truncation rather than rounding, so tax and discount computations systematically lose up to a cent per line in the customer's favour/detriment inconsistently.
FINDING: app/tasks.py | `run_task` calls `getattr(handlers, fn_name)` without verifying the result is callable, and `config.get("TASK_HANDLER_PREFIX")` returning `None` would raise `TypeError` on concatenation before the lookup.
FINDING: app/tasks.py | Dynamic `getattr` dispatch on the whole `handlers` module means any module-level attribute starting with `on_` is remotely invocable via a caller-controlled `name`, with no allowlist of registered task handlers.
