Reviewed `app/db.py` in the context of its callers (`repository.get_order` → `db.fetch_order_row` → `connect`).

FINDING: app/db.py | `fetch_order_row` closes the connection only on the happy path — if `cur.execute()` or `fetchone()` raises (locked DB, missing `orders` table, bad schema), `conn.close()` is skipped and the connection/file handle leaks; it needs `try/finally` or `contextlib.closing`.
FINDING: app/db.py | The docstring promises "None if there is no such order", but any sqlite3 error (OperationalError/DatabaseError) propagates instead, so callers like `repository.get_order` cannot distinguish "missing order" from "database failure" and will surface a raw sqlite exception.
FINDING: app/db.py | `connect()` uses `get("DB_PATH")` with no default and no validation; if the key is ever absent/None, `sqlite3.connect(None)` raises `TypeError` at call time rather than failing with a clear configuration error.
FINDING: app/db.py | A brand-new connection is opened and closed on every single call, and `repository.get_order` calls it in a retry loop, so each retry pays full connect/close cost — there is no connection reuse, pooling, or caching.
FINDING: app/db.py | `sqlite3.connect()` is called without a `timeout` (defaults to 5s) and without `isolation_level`/`check_same_thread` consideration, so concurrent writers cause an unhandled `OperationalError: database is locked` that propagates out of the "read" API.
FINDING: app/db.py | The function returns a bare positional tuple with no `row_factory` (e.g. `sqlite3.Row`), and `repository.get_order` splats it via `Order(*row)` — reordering or adding a column in this SELECT silently misassigns fields (e.g. `discount_pct` into `total_cents`) with no error.
FINDING: app/db.py | The SELECT hardcodes five columns whose count/order must exactly match the `Order` constructor arity; there is no guard, so any schema/model drift produces a `TypeError` at construction time far from this file.
FINDING: app/db.py | Returning `None` for a nonexistent order combined with the caller's retry loop means a genuinely missing id is re-queried `MAX_RETRIES + 1` times against the database, which is pure wasted I/O since a missing row will never appear mid-loop (and no exception is retried, so the retry logic is dead weight).
FINDING: app/db.py | The cursor is never explicitly closed (it is only reclaimed when the connection is closed), so on the exception path above both the cursor and connection remain open until GC.
FINDING: app/db.py | There is no `LIMIT 1` and no assumption check that `id` is unique/primary key — `fetchone()` silently discards any duplicate matching rows rather than signalling a data-integrity problem.
FINDING: app/db.py | No logging or context is attached on failure (order_id, DB path), making production diagnosis of a failed read impossible from this layer.
FINDING: app/config.py | `MAX_RETRIES: 0` makes `repository.get_order`'s `attempts = 0 + 1` a single attempt, so the documented retry behavior is effectively disabled — worth confirming whether `MAX_RETRIES` is meant to be "total attempts" or "extra retries" since `db.fetch_order_row` never raises retryable errors in a catchable way.
